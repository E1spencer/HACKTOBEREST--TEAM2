# 07: AI Service Matching

**Goal:** A client types what they need ("I need someone to help my daughter with JSS2 maths on weekday evenings"), and the system returns a ranked shortlist of real agents. The client picks. **The AI never books, pays, or invents agents.**

## Design principle (ADR-005)

```
User text --> [LLM: intent extraction, structured JSON] --> [Deterministic search + ranking (file 05)]
          --> [LLM: short, grounded explanation per agent (optional)] --> client chooses
```

The LLM understands language; the database decides who exists. This prevents hallucinated agents, keeps ranking auditable, and makes costs predictable.

---

## Prompt 7.1: LLM abstraction and prompt management

```text
In the AiMatching module create:
- ILlmClient { Task<LlmResult<T>> CompleteStructuredAsync<T>(LlmRequest request, JsonSchema schema, CancellationToken ct) }
  with adapters AzureOpenAiClient and AnthropicClient selected via configuration. Include timeout (10s),
  retry with jitter (Polly), circuit breaker, token usage + latency + cost metrics, and a FakeLlmClient for tests.
- Prompt templates stored as versioned embedded resources (/Prompts/v1/intent_extraction.txt), never inline strings.
  Each AiSearchSession records prompt version and model.
- Input guardrails: max 500 chars, strip control characters, detect prompt-injection patterns
  ("ignore previous instructions", role-play attempts) and treat user text strictly as data inside delimiters.
- Output guardrails: validate the JSON against the schema; on invalid output retry once, then fall back to keyword search.
- PII minimization: do not send names, phone numbers, or exact addresses to the LLM. Send only the free-text need
  (with regex redaction of phone/email) and the coarse city.
```

---

## Prompt 7.2: Intent extraction

```text
Implement IntentExtractor. Given the user's text and the category tree (slug + name + keywords, compacted),
return this JSON (validate with a schema):

{
  "isServiceRequest": true,
  "categorySlug": "home-tutoring-math" | null,
  "alternativeCategorySlugs": ["..."],
  "summary": "Maths tutoring for a JSS2 student",
  "schedule": { "dateHint": "weekday evenings", "earliest": null, "latest": null, "durationHours": null, "recurring": true },
  "location": { "mentioned": null, "useProfileAddress": true },
  "budget": { "maxPerHourMinor": null, "currency": null },
  "preferences": { "language": null, "genderPreference": null, "verifiedOnly": null, "minRating": null },
  "clarifyingQuestion": null,
  "confidence": 0.0-1.0
}

Rules in the system prompt:
- Choose ONLY from the provided category slugs; if none fit, set categorySlug null and isServiceRequest per intent.
- If confidence < 0.6 or critical info is missing (no category), return ONE short clarifyingQuestion.
- Never output free text outside JSON. Never invent categories, agents, or prices.
- Support multiple languages and informal phrasing (including local slang and Pidgin-style English).
- Out-of-scope requests (medical advice, illegal, adult) -> isServiceRequest=false with a polite refusal flag.

Create a golden dataset of at least 80 labeled utterances (/tests/AiEval/intent_cases.jsonl) covering
each category, vague requests, multi-intent, typos, budget phrases ("under 3k per hour"), and adversarial prompts.
```

## Prompt 7.3: Matching orchestrator and API

```text
Implement:
POST /api/v1/ai/match  {message, sessionId?, lat?, lng?, addressId?}
  1. Extract intent. If clarifyingQuestion exists, return {type:"clarification", question, sessionId}.
  2. Map intent to AgentSearchQuery (file 05). Merge client's saved address, radius default, budget, filters.
  3. Execute deterministic search; if < 3 results, progressively relax constraints in this order:
     radius -> budget (+20%) -> alternative categories -> minRating, and record which relaxations applied.
  4. Return top 5: {type:"matches", sessionId, interpretedRequest (human-readable chips the user can edit),
     relaxations[], agents[{...search item fields, matchReasons[]}]}
  5. matchReasons are generated by TEMPLATES from real data ("4.9 rating from 112 reviews", "2.1 km away",
     "Available Tue 6pm") and not free LLM text, so nothing can be hallucinated. (Optional later: LLM-polished
     summary constrained to the supplied facts.)
- POST /api/v1/ai/sessions/{id}/select {agentId} records the chosen agent (for quality metrics) and returns a
  booking-prefill payload (service, suggested time, address) for the booking flow.
- Conversation state: keep the last 6 turns per session (Redis or DB) so "make it cheaper" or "someone female" refines
  the previous intent instead of starting over.
- Rate limit 10 requests/min/user; daily cap per user; cost guard that disables AI and falls back to normal
  search when the monthly budget is exceeded.
- Streaming: expose the same flow via SSE (/ai/match/stream) emitting events: "interpreting", "searching", "results".

Fallback: if the LLM fails, run keyword/trigram search against category keywords and return results flagged `degraded:true`.
```

## Prompt 7.4: Evaluation and monitoring

```text
Build an evaluation harness (xUnit trait `AiEval`, run nightly, not on every PR):
- Intent accuracy (category top-1 and top-3), clarification precision, refusal precision, schema-validity rate,
  p50/p95 latency, cost per request. Fail the build if accuracy drops > 3% from baseline.
- Prompt-injection suite: 30 attack strings; assert no schema violation, no data leakage, no off-policy output.
- Admin dashboard metrics: matches per day, % sessions leading to a selection, % to a booking,
  clarification rate, fallback rate, most common unmatched requests (feeds new-category decisions).
- Log full LLM request/response (redacted) to a restricted table with 30-day retention for debugging.
```

**Acceptance criteria**
- AI response never includes an agent that is not in the database result set (asserted)
- Works with FakeLlmClient in CI; live eval runs nightly
- With the LLM disabled, `/ai/match` still returns useful degraded results
- Category top-3 accuracy ≥ 90% on the golden set
